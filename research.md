Источник правды о том, **как устроен бэкенд и что из этого следует для фронтенда**. Составлен
2026-07-29 перед началом работ, кода фронта ещё нет.

Всё, что помечено как факт, прочитано в коде и приведено с `file:line`. Всё, что является
предположением, помечено словом **гипотеза**. Ничего из перечисленного не проверено запуском —
бэкенд в рамках этого исследования не поднимался.

План работ — `frontend_plan.md`. Рабочие инструкции — `CLAUDE.md`.

## 1. Что это за продукт

Пользователь заводит **профиль вымышленного персонажа** и получает сгенерированную ленту «что она
делала каждый день» за выбранный срок.

Слово «модель» в проекте перегружено трижды, поэтому в этом документе оно **не используется**
(словарь — `girl-history/profile-generation_plan.md:31-45`):

| В интерфейсе для пользователя | В коде      | Что это                                          |
| ----------------------------- | ----------- | ------------------------------------------------ |
| модель, профиль модели        | `Persona`   | персонаж: имя, промпт, аватар. Их много          |
| хроника, «неделя/месяц»       | `Chronicle` | одна сгенерированная история за период           |
| день ленты                    | `Day`       | одна запись хроники                              |
| сюжетная линия                | `StoryLine` | каркас хроники из первого прохода генерации      |
| LLM-модель (`claude-opus-5`)  | `llmModel`  | всегда с префиксом `llm`, никогда просто `model` |

Здесь и далее: **профиль** = `Persona`. Когда речь про LLM — пишу «провайдер» или «LLM».

Иерархия: профиль → много хроник → у хроники сюжетные линии и дни.

## 2. Ключевая находка: фото уже влияют на генерацию, а документы бэкенда это отрицают

Требование «сгенерировать хронику по списку фото + промпт либо просто по промпту» **бэкенд уже
поддерживает**. Цепочка проверена целиком, от эндпоинта до текста промпта:

| Шаг         | Где                              | Что происходит                                                         |
| ----------- | -------------------------------- | ---------------------------------------------------------------------- |
| Загрузка    | `persona-image-controller.ts:43` | `POST /personas/:ownerToken/images`, multipart, поле `images`          |
| Разбор      | `persona-image-service.ts:46-68` | каждая картинка идёт в vision, описание пишется в БД                   |
| Vision      | `vision-service.ts:23-69`        | реальная отправка картинки в Anthropic (base64), ответ 3-5 предложений |
| Чтение      | `generation-service.ts:67`       | все референсы профиля читаются один раз на джобу                       |
| Сборка      | `generation-service.ts:138,177`  | передаются в `buildPersonaBlock`                                       |
| Промпт      | `prompt-builder.ts:48-59`        | блок «РЕФЕРЕНСНЫЕ ИЗОБРАЖЕНИЯ (что на них видно)» + инструкция         |
| Регистрация | `di-container.ts`                | `visionService`, `personaImageService` — оба в контейнере              |

Ветка в `prompt-builder.ts:52` включается **только** при непустых описаниях. Значит режим «просто
промпт» получается сам собой, если референсов нет: отдельного переключателя не нужно.

### Расхождение с документами бэкенда — важно не поверить им

Три документа проекта утверждают, что vision не реализован и фото в генерации не участвует:

| Документ                                     | Что написано                                                |
| -------------------------------------------- | ----------------------------------------------------------- |
| `girl-history/CLAUDE.md` §Текущее состояние  | «Этого ещё нет: … vision (`appearance` всегда `null`)»      |
| `girl-history/README.md` §Что ещё не сделано | «vision: поле `appearance` есть в схеме … но всегда `null`» |
| `girl-history/profile-generation_plan.md:9`  | «Не реализовано: фронтенд §8, vision (фаза 6)»              |

**Формально они правы только про поле `appearance`**: его действительно никто не заполняет
автоматически. При создании профиля туда жёстко пишется `null` (`persona-service.ts:44`), и
единственный, кто может его заполнить, — сам пользователь через `PATCH /personas/:ownerToken`
(`persona-dto.ts:29`). Vision его не трогает.

Но **как способность vision реализован и на текст хроники влияет** — через
`PersonaImage.description`. Утверждение «фотография в LLM не отправляется» верно **исключительно про
аватар профиля**, и там оно действительно соблюдено: аватар в `buildPersonaBlock` не попадает
(`prompt-builder.ts:38-40`).

Итого три разных сущности с фотографиями, которые легко перепутать:

| Что                | Поле / модель                  | Идёт в LLM             | Кто заполняет              |
| ------------------ | ------------------------------ | ---------------------- | -------------------------- |
| Аватар профиля     | `Persona.photoPath`            | **нет**, оформление    | пользователь, опционально  |
| Референс           | `PersonaImage` + `description` | **да**, через описание | vision при загрузке        |
| Описание внешности | `Persona.appearance`           | **да**, если не пусто  | только пользователь руками |

### Ограничение, которое надо знать до проектирования экранов

Референсы прикреплены **к профилю**, а не к хронике: `generation-service.ts:67` безусловно читает все
картинки профиля при каждой генерации. Поэтому выбор «с фото / без фото» сегодня делается **один раз
при настройке профиля**, а не при каждом запуске хроники. Чтобы у одного персонажа получить одну
хронику с фото и другую без — потребуется правка бэкенда (дёшево: булев флаг на `Chronicle`; гибко:
выбор конкретных картинок при создании хроники).

**Решение на 2026-07-29:** делаем на уровне профиля, бэкенд не трогаем.

## 3. Карта API — снята с контроллеров, не с плана

Маршруты регистрируются **без** префикса `/api` (`app.ts:73-86`): его снимают Nginx на проде и
Vite-прокси в деве. Ответ об ошибке всегда `{ error: string }`, у ошибок валидации добавляется
`details` (`http-helpers.ts:23-34`).

### Профили — `persona-controller.ts`

| Метод    | Путь                    | Код | Тело / ответ                                                    |
| -------- | ----------------------- | --- | --------------------------------------------------------------- |
| `POST`   | `/personas`             | 201 | multipart: `name`, `sourcePrompt`, `photo?` → `PersonaOwnerDTO` |
| `GET`    | `/personas`             | 200 | `?limit=&offset=` → `PersonaListDTO`                            |
| `GET`    | `/personas/:ownerToken` | 200 | `PersonaOwnerDTO` (с промптом и списком хроник)                 |
| `PATCH`  | `/personas/:ownerToken` | 200 | multipart, частичное тело + `photo?` → `PersonaOwnerDTO`        |
| `DELETE` | `/personas/:ownerToken` | 204 | каскадом сносит хроники, дни, джобы, файлы                      |

`limit` режется до 100, `offset` не может быть отрицательным (`persona-controller.ts:38-39`).
PATCH с пустым телом и без файла → 400 «Нечего обновлять» (`persona-controller.ts:63-65`).

### Референсы — `persona-image-controller.ts`

| Метод    | Путь                                            | Код | Примечание                                 |
| -------- | ----------------------------------------------- | --- | ------------------------------------------ |
| `GET`    | `/personas/:ownerToken/images`                  | 200 | `{ items, total }`                         |
| `POST`   | `/personas/:ownerToken/images`                  | 201 | multipart, поле `images`, несколько файлов |
| `PATCH`  | `/personas/:ownerToken/images/:imageId`         | 200 | `{ description }` — правка руками          |
| `POST`   | `/personas/:ownerToken/images/:imageId/analyze` | 200 | повторный разбор vision                    |
| `DELETE` | `/personas/:ownerToken/images/:imageId`         | 204 |                                            |

### Хроники, владельческие операции — `owner-chronicle-controller.ts`

Все под `/personas/:ownerToken/...`, чтобы `publicToken` и `ownerToken` никогда не оказывались в
одной позиции пути.

| Метод    | Путь                                                           | Код | Тело / ответ                                                              |
| -------- | -------------------------------------------------------------- | --- | ------------------------------------------------------------------------- |
| `POST`   | `/personas/:ownerToken/chronicles`                             | 202 | `{periodDays, startDate?, promptExtra?, provider?}` → `{id, publicToken}` |

> регенерацию как `/chronicles/:ownerToken/...`. В коде они под `/personas/...`
> (`owner-chronicle-controller.ts:14`). Верить коду.

### Хроники, чтение — `chronicle-controller.ts`

| Метод | Путь                              | Ответ                                      |

## 4. Права и токены

| Токен         | На чём      | Где живёт             | Что даёт                          |
| ------------- | ----------- | --------------------- | --------------------------------- |
| `ownerKey`    | у владельца | localStorage браузера | увидеть свой список профилей      |
| `ownerToken`  | на профиле  | у создателя           | вся правка: профиль, хроники, дни |
| `publicToken` | на хронике  | в ссылке для чтения   | только чтение одной хроники       |

Механика `ownerKey`, которую **нельзя пропустить** (`http-helpers.ts:13-20`):

- заголовок `x-owner-key`, используется только на `POST /personas` и `GET /personas`;
- если клиент не прислал ключ **или прислал короче 16 символов** — сервер молча генерирует новый и
  кладёт его в заголовок **ответа**;
- фронт обязан прочитать заголовок ответа и сохранить. Не сохранил — каждый запрос считается новым
  владельцем, и список профилей всегда пуст;
- CORS настроен на выдачу этого заголовка наружу (`app.ts:32`), так что и без прокси он читается.

`ownerToken` приходит в списке профилей (`PersonaListItemDTO.ownerToken`, `persona-dto.ts:88`), то
есть цепочка такая: `ownerKey` → список → `ownerToken` каждого профиля → все остальные операции.

**`ownerToken` — секрет.** Это право удалить профиль со всем содержимым. Публичная ссылка строится на
`publicToken`, и путать их нельзя.

**Владелец читает дни по `publicToken`.** В `OwnerChronicleController` нет ни одного `@GET` — там
только запись. Ленту, статус и линии отдаёт публичный контроллер, и другого пути нет. Значит
`publicToken` нужен владельцу для повседневной работы, а не только чтобы поделиться ссылкой; он
приходит в `ChronicleSummaryDTO.publicToken` вместе со списком хроник профиля.

## 5. Генерация: что видит фронт

Два прохода (`generation-service.ts:70-102`): сначала скелет сюжетных линий, потом дни внутри каждой
линии, линии строго последовательно. Всё фоновое — ответ на создание хроники приходит сразу, `202`.

Статусы джобы (`job-repository.ts:3-4`):

| Статус    | Значение                                                             |
| --------- | -------------------------------------------------------------------- |
| `pending` | создана, ещё не начата                                               |
| `running` | идёт; стадия в поле `stage`: `skeleton` → `days`                     |
| `done`    | готово                                                               |
| `partial` | **упало на середине, но часть дней записана и осталась** — не провал |
| `failed`  | упало, не записав ни одного дня                                      |

`partial` выставляется, когда `doneDays > 0` на момент ошибки (`generation-service.ts:107`). Повтор
дозаполнит недостающее. В интерфейсе это должно выглядеть иначе, чем `failed`.

Три состояния сервера, которые дают 409 и которые фронт обязан предвидеть:

| Ситуация                                        | Где                          | Что делать в UI                                |
| ----------------------------------------------- | ---------------------------- | ---------------------------------------------- |
| Генерация уже идёт по **любой** хронике профиля | `chronicle-service.ts:55-58` | гасить запуск у всех хроник этого профиля      |
| Правка дня во время активной генерации          | `day-service.ts:30-35`       | блокировать редактор, пока `pending`/`running` |
| Устаревший `updatedAt` при правке дня           | `day-service.ts:51-55`       | предложить перечитать день                     |

Про прогресс есть три тонкости, и наивный расчёт ошибётся на каждой:

1. `doneDays` увеличивается **по завершении сюжетной линии**, а не по дню (`generation-service.ts:99`).
   При линии в 10 дней полоса стоит, потом прыгает на десять делений.
2. `generatedDays` из `/status` — это `count` **всех** дней хроники (`day-repository.ts:94-96`), а
   `totalDays` при выборочной регенерации равен длине выбранного диапазона
   (`chronicle-service.ts:177`). Перегенерация 3 дней из 30 даст «30 из 3». Плюс выбранные дни перед
   регенерацией удаляются (`chronicle-service.ts:169-175`), так что счётчик сперва падает на
   неизвестную величину. Различать случаи можно сравнением `totalDays` с `periodDays` хроники:
   равны — полная генерация, `generatedDays` годится; меньше — выборочная, годится только
   `doneDays / totalDays`.
3. `doneDays` **не обязан дойти до** `totalDays`. Отредактированные руками дни пропускаются
   (`generation-service.ts:160`), но в `totalDays` посчитаны: регенерация 5 дней, из которых 2
   правлены, закончится на 3 из 5 — и джоба всё равно встанет в `done`. Завершение определять по
   полю `status`, никогда по равенству счётчиков.

## 6. Лимиты и валидация — чтобы не ловить 400/409/413 вслепую

| Что                          | Значение                          | Источник                                         |
| ---------------------------- | --------------------------------- | ------------------------------------------------ |
| `name` профиля               | 1..120 символов                   | `persona-dto.ts:11`                              |
| `sourcePrompt`               | 10..8000 символов                 | `persona-dto.ts:12-16`                           |
| `appearance`                 | до 4000, может быть `null`        | `persona-dto.ts:29`                              |
| `periodDays`                 | целое, 1..90 (`MAX_PERIOD_DAYS`)  | `chronicle-dto.ts:12`, `chronicle-service.ts:42` |
| `startDate`                  | **`YYYY-MM-DD`**                  | `chronicle-dto.ts:14`                            |
| `promptExtra`                | до 2000                           | `chronicle-dto.ts:15`                            |
| `dayIndexes` при регенерации | массив до 400 элементов           | `chronicle-dto.ts:23`                            |
| `expectedUpdatedAt`          | **полный ISO datetime**           | `day-dto.ts:26`                                  |
| День: `title` / `text`       | 1..200 / 1..8000                  | `day-dto.ts:18-19`                               |
| День: `mood`                 | до 80, может быть `null`          | `day-dto.ts:20`                                  |
| День: `activityTags`         | до 12 штук, каждый до 40 символов | `day-dto.ts:21`                                  |
| Референсов на профиль        | 5 (`MAX_PERSONA_IMAGES`)          | `server-config.ts:42`                            |
| Файлов в одном запросе       | 10 (multer)                       | `upload.ts:24`                                   |
| Размер файла                 | 5 МБ (`MAX_UPLOAD_BYTES`)         | `server-config.ts:53`                            |
| Хроник на профиль            | 20                                | `server-config.ts:62`                            |
| Лимит записи                 | 60 / 15 мин                       | `rate-limit.ts:8-14`                             |
| Лимит запусков генерации     | 15 / 15 мин (четверть от записи)  | `rate-limit.ts:17-23`                            |

Два формата дат легко перепутать: `startDate` — `YYYY-MM-DD`, `expectedUpdatedAt` — полный ISO с
временем. Разные схемы zod, обе строгие.

Чтение (`GET`) не лимитируется вовсе — лимитеры навешены только на пишущие маршруты. Значит поллинг
статуса безопасен и лимит генерации не ест.

Но лимитеры разложены не так, как подсказывает интуиция. Под **жёстким** `generationLimiter`
(15 запросов / 15 мин) сидят четыре маршрута, включая работу с фотографиями:

| Маршрут                                                      | Лимитер                    | Где                                |
| ------------------------------------------------------------ | -------------------------- | ---------------------------------- |
| `POST /personas/:ownerToken/chronicles`                      | `generationLimiter`        | `owner-chronicle-controller.ts:29` |
| `POST .../chronicles/:chronicleId/regenerate`                | `generationLimiter`        | `owner-chronicle-controller.ts:43` |
| **`POST /personas/:ownerToken/images`** (загрузка фото)      | `generationLimiter`        | `persona-image-controller.ts:45`   |
| **`POST .../images/:imageId/analyze`** (повторный разбор)    | `generationLimiter`        | `persona-image-controller.ts:79`   |
| Всё остальное пишущее (профиль, правка дня, правка описания) | `writeLimiter` (60/15 мин) | —                                  |

Практическое следствие: несколько повторных разборов референсов подряд съедают тот же лимит, что и
запуск генерации, и кнопка «Сгенерировать» ответит 429. В интерфейсе это надо предупреждать.

## 7. Как устроен `ai-prompt-admin` — образец архитектуры

Разбор нужен, чтобы повторить структуру и **не повторить** её слабые места.

### Что берём

- **Vite + TypeScript, без React/Vue.** Зависимости фронта: `vite`, `axios`, `chart.js` — всё
  (`ai-prompt-admin/package.json`).
- **Один `index.html`**, вся навигация — вкладки, `<script type="module" src="/src/app.ts">`
  (`index.html:129`).
- **`src/app.ts` — класс `App`**: `setupTabs()`, `activateTab(name)`, компоненты создаются **при
  первой активации вкладки** и дальше переиспользуются (`app.ts:49-107`). Ленивость — хорошая идея:
  тяжёлые вкладки не грузят данные, пока их не открыли.
- **Компонент = класс** в `src/modules/<фича>/<фича>-component.ts` с одинаковым контрактом
  (`clothing-component.ts:5-56`):

  ```
  constructor(containerId)  → находит контейнер, renderLayout(), bindEvents()
  renderLayout()            → innerHTML разметки вкладки
  bindEvents()              → подписки на кнопки
  activate()                → загрузка данных, вызывается при открытии вкладки
  ```

- **`src/api/api.ts`** — объекты-неймспейсы (`PromptsAPI`, `LlmAPI`, …) поверх одного axios-инстанса
  с `baseURL = '/api'` (`api.ts:9-14`).
- **`src/types/*.ts`** — интерфейсы, зеркалящие DTO бэкенда.
- **Схема прокси** (`vite.config.ts`): `/api` → бэкенд, `rewrite` снимает префикс.

### Что НЕ берём — конкретные проблемы этого кода

| #   | Проблема                                                                        | Где                                                     | Как делаем у себя                             |
| --- | ------------------------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------- |
| 1   | `eslint.config.js` **закомментирован целиком** — линта фактически нет           | `eslint.config.js` — все 42 строки                      | рабочий конфиг, `no-explicit-any: error`      |

### Главное следствие для фронта: префикс картинок различается между окружениями

`PUBLIC_URL_PREFIX` на проде = `/girl-history` (`.env.production:65`), локально пуст (`.env`).

| --------- | ----------------------------------- |
| локально  | `/media/871d5eb5….png`              |

**Отсюда два правила, обязательных к соблюдению:**

1. **Никогда не конструировать URL картинки самим** — брать `photoUrl` и `images[].url` из ответа как
